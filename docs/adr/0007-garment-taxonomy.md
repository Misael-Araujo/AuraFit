# ADR 0007: Wardrobe garment taxonomy and wishlist metadata

- **Status:** Accepted
- **Context:** The wardrobe module needs a stable model for clothing records that can be user-edited after AI extraction. The metadata includes category/subcategory, color family, season, occasion tags, material, brand, and purchase information for wishlist items. The taxonomy must remain flexible enough for user corrections while still supporting filter-driven queries and backend validation.
- **Decision:** Use a small enum-based taxonomy for the high-volume, controlled fields (`source`, `status`, `season`, `occasion`) and free-form strings for the user-editable metadata fields (`category`, `subcategory`, `colorFamily`, `pattern`, `material`, `brand`, `size`, and notes`). The API treats garment metadata as editable because AI extraction is a best-effort guess, not a source of truth. Wishlist entries keep a validated `purchaseUrl` and `price`, but server-side fetching of remote product pages stays out of scope in this phase to avoid SSRF risk.
- **Consequences:** The model supports fast filtering and simple validation without introducing a large reference-table layer for every garment tag. User edits remain easy because metadata is not locked to a fixed taxonomy. The trade-off is that some values remain free text, which requires validation and a stable canonicalization policy if future analytics or recommendation services need stronger consistency.
- **Alternatives:** A fully normalized reference-table design would be more rigid and would add more database joins for common list queries; this is rejected for the MVP because the core requirement is user-editable metadata rather than strict controlled vocabulary.
